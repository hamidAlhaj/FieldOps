# Stage 4 — مراجعة الواجهات بعد إدارة المؤسسة والحساب

المرحلة غير مغلقة بالكامل: Tracking وSmart Dispatch ما زالا يعتمدان على Backend غير منفذ منStage6. لم تُعرض مواقع وهمية ولم يُفعّل مكوّن الموافقة غير المكتمل.

| الواجهة | حالة النسخة الحالية |
| --- | --- |
| Login / Registration | موجودتان وتسجيل فعلي وجلسات واستعادة آمنة |
| Admin Dashboard | Overview مع روابط الإدارة والتقارير والتدقيق؛ إدارة العضويات والفرق وإعداد اسم المؤسسة أصبحت فعلية |
| Dispatcher Dashboard | Overview وقائمة الأعمال والتعيين والمتابعة والتقارير؛ الخريطة والتوصيات الذكية غير متاحتين |
| Technician Dashboard | الأعمال المصرح بها والقبول والتنفيذ والصور والتقدم؛ التتبع غير مفعّل |
| Customer Portal | إنشاء الطلبات ومتابعة الطلب والأعمال المملوكة |
| Work Order Management | دورة العمل الأساسية؛ لا جدولة متقدمة تمنع تداخل مهام مختلفة |
| Maintenance Request Details | مراجعة وإلغاء وتحويل إلىعمل حسب الدور والحالة |
| Assignment Interface | تعيين وإعادة تعيين يدويان؛ Smart Dispatch ناقص منStage6 |
| Live Tracking Map | غير منفذة؛ تحتاج Tracking Backend والجلسات وexpiry وصلاحيات الموقع |
| Notifications Center | قائمة وتعليم مقروء وتفضيل استقبال تنبيهات التعيين؛ unread counter وإشعارات تغيّر الحالة ما زالا ناقصين |
| Analytics and Reports | موجودة مع بيانات فعلية وحدودها كما فيreporting.ar.md |
| Profile and Settings | حفظ displayName والثيم وتنبيهات التعيين، وتغيير كلمة المرور؛ البريد غير قابل للتغيير دونverification |

## الإضافات والقرارات

- `AdministrationModule` يوفر البحث والفلاتر وpagination من الخادم؛ 25 عضوية في الصفحة. الوصول للـAdmin داخل مؤسسته فقط باستخدام Guards وRLS.
- إضافة المستخدم تتم عبر بريد حساب مسجل مسبقاً. حماية آخر Admin وقواعد تغيير الأدوار المرتبطة بـProfiles تبقى في AuthService.
- إدارة الفرق تشمل الإنشاء والتسمية وإضافة وإزالة الأعضاء. حذف الفريق يرفض وجود WorkOrders مرتبطة به، وإلا يحذف العضويات والفريق داخل transaction. قائمة الفرق محدودة بـ100، واختيار الموظف يستخدم صفحة المستخدمين الحالية مع البحث.
- إعداد المؤسسة المدعوم هو الاسم. لا توجد عناصر تحكم تدّعي حفظ إعدادات غير منفذة.
- Profile يستخدم React Hook Form وZod. لا يقبل API تعديل البريد أوحقول هوية إضافية. تفضيل تنبيهات التعيين يؤثر على إنشائها، ولا يغيّر صلاحيات الأعمال.
- الثيم محفوظ في قاعدة البيانات ويُحمّل عند الدخول، مع بقاء التبديل السريع المحلي.
- تغيير كلمة المرور يتحقق من الحالية بـArgon2 ويقفل User أثناء transaction، ثم يلغي جميع AuthSessions وRefresh cookie. Login يقفل نفس الصف ويعيد فحص hash لمنع إصدار جلسة بكلمة قديمة عند التزامن. بعد التغيير تُمسح هوية العميل وcache ويُطلب تسجيل الدخول.

## التشغيل والتحقق

```bash
npm run db:generate
npm exec -w @fieldops/api -- prisma migrate deploy
npm run dev
npm run typecheck
npm test
npm run build
```

migration008 تضيف تفضيلات الحساب وصلاحية تحديث اسم المؤسسة المحددة، وطُبقت على development وtest دون reset. اختبارات التكامل تحتاج TEST_DATABASE_URL لقاعدة مستقلة تنتهي بـ_test.

نجح typecheck وbuild و28 اختباراً عادياً و51 اختبار تكامل. تشمل الاختبارات الجديدة حفظ الملف، رفض تعديل البريد، كلمة المرور الخاطئة، إبطال الجلسات، عضوية فريق من مؤسسة أخرى والحذف. أضيفت لاختبار المتصفح إجراءات إنشاء فريق وحفظ الملف وإعادة تحميله، مع لقطات للواجهتين. نجح اختبارا API browser بعد إعادة محاولة التقاط الشاشة بمهلة مناسبة وإيقاف الحركة.

الواجهات تعيد استخدام CSS وworkflow cards والثيمات الموجودة. فحص المتصفح لا يمثل اختبار كل إجراء إداري على كل مقاس. تبقى Stage4 جزئية بسبب اعتماد الخريطة وSmart Dispatch وتغطية الإشعارات على Stage6. لم يُعد فحص vulnerabilities في هذه الدفعة؛ تبقى حدود الإنتاج السابقة موثقة.
